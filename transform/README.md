# transform/ : the external-to-internal transform (B6)

This directory holds the flagship button of the ver.cy registry: the
deterministic transform that takes one external standard from the unified
registry and instantiates an internal tenant meta-model from it, overlaying the
ver.cy governance and recording full lineage back to the external source.

The formula, made a single operation:

```
external-to-internal = Extension-Model + Policy-Consistency + Data-Mastership
```

## What is here

| Path | What it is |
|---|---|
| `EXTERNAL-TO-INTERNAL.md` | The normative transform specification: the formula, the inputs and outputs, the six steps, the MAPPING table, the B6 invariants, the conformance rules, and the worked example. |
| `policy-profiles/vercy-baseline.yaml` | The default policy profile: the ver.cy governance overlay. It carries `default_delegation_tier` and the ordered list of policy ids the transform records in `applied_policies`. |

The tool itself lives at `tools/instantiate.py` (the button), its output entries
land in `entries/`, and its manifests land in `instantiations/`. The admission
check is `ci/check_instantiations.py`, wired into `ci/run.py` after
`check_facets`.

## How to run tools/instantiate.py

From the registry root:

```
python tools/instantiate.py --external <registry_ref> --tenant <tenant> \
    --profile <profile> --at <iso8601>
```

- `--external` (also accepted as `--standard`): the Acronym, or the Name when
  there is no Acronym, of the row in `external/external-standards.csv` to
  instantiate.
- `--tenant`: the party instantiating the model, a simple lowercase token. It
  becomes the publisher, owner and steward of the new internal record.
- `--profile`: the policy profile id, default `vercy-baseline`, resolving to
  `policy-profiles/<profile>.yaml`.
- `--at`: an ISO-8601 timestamp. The transform reads no wall clock, so the
  timestamp is an explicit input, which is what makes a run reproducible.

The tool writes two artifacts and is a pure function of its inputs:

1. `entries/<internal_id>.yaml`, the internal Model Registration Record (a
   first-class MMDG node the resolver can compose, picked up by
   `tools/build_index.py`); and
2. `instantiations/<instantiation_id>.manifest.json`, the instantiation manifest
   recording how the external model was bound, which policies were overlaid, who
   masters the data, and the lineage.

## Committing an instantiation: four artifacts, not two

Running the tool produces the entry and the manifest, but committing a real
instantiation is a four-artifact operation. The new node enters the unified index
and shifts the resolver's registry-wide coverage line, so after running the tool
the operator regenerates the two generated artifacts and commits all four
together:

```
python tools/instantiate.py --external <ref> --tenant <t> --profile <p> --at <iso8601>
python tools/build_index.py
# then regenerate the resolver fixtures under examples/expected/ via resolver/resolve.py
```

Commit together: the new `entries/<internal_id>.yaml`, the new
`instantiations/<instantiation_id>.manifest.json`, the refreshed
`index/unified-index.json`, and the regenerated `examples/expected/` fixtures.
`check_facets` fails on a stale unified index and `check_resolve` fails on a stale
resolver fixture, so shipping only the entry and the manifest turns the gate red.
See the main registry README for the same four-step regen flow.

## The worked example

The worked example instantiates HL7 FHIR for tenant `acme` at a fixed timestamp:

```
python tools/instantiate.py --external FHIR --tenant acme \
    --profile vercy-baseline --at 2026-08-10T00:00:00Z
```

The worked-example entry and manifest are not hand-written; they are generated by
running the command above and committed as fixtures (with the refreshed index and
resolver fixtures, per the four-artifact flow above) by the operator after the
workflow. `ci/check_instantiations.py` replays each committed instantiation and
byte-compares the result, so the example is reproducible byte for byte.

## The profile concept

A policy profile is the Policy-Consistency term of the formula, made concrete. It
is the named set of ver.cy governance controls the transform overlays on every
model it instantiates. The default, `vercy-baseline`, carries:

- the eight Common Operating Law invariant controls IC-1 to IC-8, cited by id and
  never restated (IC-1 one master per dataset, IC-3 data is never a command, IC-8
  append-only, and the rest);
- the mastership stance (the external source is the System of Record, the flow is
  inbound, the internal model references and overlays governance and never masters
  the external semantics, per ARCH-018);
- the append-only stance (supersession, not deletion, per IC-8); and
- the profile-level policies that bind the transform to its machinery:
  `mastership-external` (ARCH-018), `lineage-required` (Provenance-Graph),
  `policy-consistency` (ARCH-014) and `extension-binding` (Extension-Model).

The profile also sets `default_delegation_tier: T1`: a fresh instantiation starts
human-in-the-loop, the transform proposes and a human approves each act. T3 is
never a starting tier; it is earned along the ladder T1 to T2 to T3 (Common
Operating Law section 3).

The ordered list of policy ids under `policies:` is exactly the set the transform
lists in `applied_policies`, so the overlay is closed over the profile it names
(ARCH-014): every applied policy is a declared policy. To define a different
overlay, add another file under `policy-profiles/` and pass its id to `--profile`.
