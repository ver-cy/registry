# Contributing to the Vercy meta-model registry

Thank you for considering a contribution. This repository follows the ethos it implements: the write path is a governed proposal, and governance lives on the write path because governance that is not on the write path does not exist.

## How to propose a change

1. **Open a pull request.** Every change to an entry, to the edge file, to the schemas, or to the resolver arrives as a pull request. There is no other write path. Issues are welcome for discussion, but nothing becomes part of the registry without a merged pull request.
2. **One node per pull request is fine.** A proposal that adds a single `entries/<id>.yaml` and its edges is the normal, encouraged shape. Small and reviewable beats large and coupled. You do not need to register several models at once, and you should not.
3. **The propose-only ethos.** A pull request is a proposal, not a commit. Merging an entry publishes a discovery record that points at a source the registry does not own; it never copies or mutates the model. Registration does not transfer ownership. This repository never masters domain data, so there is no path here that writes into a mastered source at all.
4. **CI must pass, fail-closed.** Every pull request runs four checks:
   - **Schema validation.** Every entry validates against the ELMM node profile, and its projected upstream field subset validates against the upstream Meta-Universe registry-entry schema; every record in `mmdg/edges.json` validates against the edge schema.
   - **Graph integrity.** Both endpoints of every edge exist in `entries/`; every kind a `references` edge names appears in the target's `exports`; each `requires` `min_version` equals the `declared_min` of the corresponding edge; `composes` is acyclic; no `composes` or `references` edge leaves the kernel node; and registry ids are unique.
   - **Resolver determinism and output validity.** The resolver runs on the worked task and its output validates against the context-pack and Twin Composition Snapshot schemas; the example fixtures under `examples/expected/` are regenerated by running the resolver, and a proposal that changes resolution must regenerate them; a stale fixture is a red check.
   - **Zero-change registration.** A demonstration model registers by adding one entry and its edges, with no change to the schemas or the resolver.
   A red check blocks merge, no exceptions. Humans enter the loop only for ARCH-014 scope escalations.

## Ground rules

- **Satisfy both schemas.** An entry is a registry record and an MMDG node at once. Carry the upstream fields and the profile fields, and map `kind` from `role` (`core` to `domain`, `landscape` and `kernel` to `enterprise`). `role` governs; `kind` is retained for upstream tooling. The upstream check runs on the projected upstream field subset because the upstream schema is `additionalProperties: false`; the extension fields ride change requests CR-1 and CR-2.
- **Identity is registry id plus Canonical Semantic Name and Namespace (ARCH-003).** The semantic pin is the Semantic Fingerprint (ARCH-009), never a byte hash. Byte-level digests such as `edges_hash` and `source_ref` are permitted only as clearly labeled non-semantic transport-integrity fields.
- **Bind by reference, never restate.** If the Meta-Universe standard already defines a mechanism (identity, versioning, composition, validation, federation, projection, mastership), cite its ID and do not re-specify it here. The one genuinely new artifact is the MMDG edge record.
- **Enumerations are illustrative.** No list of models in any document is normative. The normative set is the contents of `entries/`.
- **English only, vendor-neutral, standalone.** No product names in the registry content, no private repository paths, no non-English sources cited as authority.
- **Determinism is mandatory in executable paths.** The resolver and CI must be bit-reproducible. No wall-clock time and no randomness: timestamps come from CLI arguments or input fields, and `snapshot_id` is derived deterministically. A change that introduces a clock or a random source into an executable path will be rejected.
- **Respect the cut line.** v0.1 is a walking skeleton: one registry, one resolver, CI, no services. Proposals that add services, controllers, buses, or protocol surfaces belong in the Deferred section of the ELMM spec with a named activation trigger, not here.
- **Decisions the spec marks adopted are not reopened by pull request.** Minimal Version Selection over declared minimums, the four edge types, identity as registry id plus CSN and Namespace with the Semantic Fingerprint as the semantic pin, and the propose-only write path are settled. File an issue with new evidence instead.
