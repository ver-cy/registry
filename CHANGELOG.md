# Changelog

All notable changes to the Vercy meta-model registry are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html) with versioning semantics per Meta-Universe ARCH-002. Major versions of any registered model are distinct registry identities and may coexist.

## [Unreleased]

### Added

- A reproducible Bitrix delivery projection under `deployment/bitrix/`. It keeps desired subject meta-models (`vercy_models`) separate from external interoperability references (`vercy_interoperability`), publishes the former through the live `/models/` catalogue, routes dedicated TODO pages for not-yet-specified models, and includes dynamic entries in the sitemap. Bitrix is explicitly a projection and administration surface, not the registry's semantic source of truth.
- The Enterprise Landscape as a registered Level-2 Landscape node, `vercy.enterprise-landscape` (`entries/vercy.enterprise-landscape.yaml`). It composes the software Core (`vercy.aismm`, entity) and the product Landscape (`vercy.plmm`, product and capability) by reference, with two `composes` edges in `mmdg/edges.json` (R2 to AISMM, R6 to PLMM). It is the neutral registration of enterprise-model content developed with a collaborator; the populated domain content stays in the source model and is referenced, never hosted. The name deliberately avoids the EMM / AIEMM / ELMM homographs: ELMM is the thin Level-3 kernel, this node is a populated Level-2 Landscape. The organization model (proposed neutral id `vercy.omm`) is a deferred reference, not yet registered, so no edge names it: an absent active member stays a known unresolved reference, never a shadow owner.
- `ci/check_taint.py`, an eighth fail-closed admission check wired into `ci/run.py`, with the portable detector `ci/taint_gate.py`. It fails closed on any commercial coupling in a canonical-identity position (schema `$id` or title, the value of an id / model_id / csn / namespace / display_alias key, or a file or directory name under `registry/` or `schemas/`), while exempting free-text evidence and source-repository URLs. Neutrality is now guaranteed on the write path (ELMM-I39), not just by review.

### Changed

- Neutralized the AISMM node identity: `orkestron.aismm` becomes `vercy.aismm` (publisher and owner Vercy, home `github.com/ver-cy/software-meta-model`), removing commercial coupling from the open-standard registry. Graph-consistent across entries, edges, the index, the resolver fixtures and the walkthrough. The form `ver-cy.aismm` is not used: the `model_id` pattern forbids a hyphen in the publisher prefix, and every other node uses the `vercy.` prefix.

## [0.3.0] - 2026-08-10

### Added

- The external-to-internal transform (workstream B6): the single deterministic operation that promotes one external standard, one row of `external/external-standards.csv`, into an internal tenant meta-model. The result is a new Model Registration Record that is a first-class MMDG node the resolver can compose, plus an instantiation manifest recording exactly how the crossing was made. This is the moment an external reference crosses the boundary the unified registry named and deferred in v0.2. The operation is the owner's formula made one step: external-to-internal = Extension-Model + Policy-Consistency + Data-Mastership, composed by ARCH-016 (`Meta-Model-Composition`), and it adds no new theory, only the wiring.
- `transform/EXTERNAL-TO-INTERNAL.md`, the normative transform spec, with `transform/README.md` and the default overlay `transform/policy-profiles/vercy-baseline.yaml`. The profile overlays the eight invariant controls of the Common Operating Law (IC-1 to IC-8) on every instantiation and starts a fresh instantiation at delegation tier T1 (human-in-the-loop). IC-1 (one master per dataset, declared never inferred) is why mastership is declared, not implied; IC-3 (data is never a command) is why an instantiated external model is classed `mirrored-external`, therefore data, never instructions. Policy consistency across the overlaid controls binds to ARCH-014.
- The binding the transform emits: an AISMM `external_binding` block (the established shape `target`, `composition_kind`, `link_type`, `standard_id`, `version`). The `link_type` is derived from the standard's `DefaultLinkType` and the `composition_kind` from its `CompositionalRole` (R1 to R8, ARCH-016), with the AISMM conditional that a `value_object` forces `link_type` `embed`. Data-mastership is declared per ARCH-018: the external source is the master, the generated entry's `source.repository` points at the standard's specification URL, and the manifest's Mastership Register stanza sets the system of record to that external source with an inbound flow. Lineage is recorded per `Provenance-Graph`: `derived_from` the external standard, the transform, and a provenance note.
- `schema/instantiation-manifest.schema.json`: a new JSON Schema (draft 2020-12) for the instantiation manifest, one file per instantiation under `instantiations/`, recording `instantiation_id`, `tenant`, `profile`, `external_ref`, `internal_id`, the `external_binding` block, the `mastership` stanza, `applied_policies`, `delegation_tier`, `lineage`, and the deterministic `semantic_fingerprint`.
- `tools/instantiate.py`, the transform (the B6 button). It reads no wall clock (the timestamp comes from a required `--at` ISO-8601 argument) and no randomness; the `instantiation_id` and `semantic_fingerprint` are deterministic hashes over canonical content, so re-running with the same inputs yields a byte-identical entry and manifest. Worked example, reproducible byte for byte: `python tools/instantiate.py --standard FHIR --tenant acme --at 2026-08-10T00:00:00Z`. FHIR is `R4` / `REFERENCE` in the catalogue, so the binding resolves to `composition_kind` entity and `link_type` reference, the `healthcare-life-sciences` industry facet is inherited verbatim, and `source.repository` is the FHIR specification URL. The generated entry and manifest are committed as fixtures by the operator after running the tool, not hand-written.
- `ci/check_instantiations.py`, a sixth fail-closed CI check wired into `ci/run.py` after `check_facets`. It regenerates each committed instantiation and diffs it, validates every generated entry against `registry-node.schema.json` at v0.3 and every manifest against `instantiation-manifest.schema.json`, and confirms the five prior checks still pass on the enlarged registry. The generated entry is a first-class node: `tools/build_index.py` indexes it and the resolver can compose it.

### Changed

- `schema/registry-node.schema.json` is extended toward v0.3, adding the optional fields `derived_from`, `external_binding`, `applied_policies` and `tenant` that an instantiated entry carries. The change is additive only: no field becomes required, every v0.2 and v0.1 constraint is kept, so the four existing internal entries, the resolver, and all five existing CI checks (`check_schema`, `check_graph`, `check_resolve`, `check_zero_change`, `check_facets`) keep passing unchanged.

## [0.2.0] - 2026-08-10

### Added

- The unified registry: one repository, two entry classes on two orthogonal facet axes. The internal meta-models under `entries/` remain the MMDG nodes (few, governed, versioned, joined by typed edges). Alongside them, `external/external-standards.csv` is a discovery catalogue of 1180 external reference standards. External standards are references, not graph nodes: a standard becomes an MMDG node only when instantiated by a future external-to-internal transform, which is out of scope for this release.
- The two orthogonal facet axes over both entry classes. `cluster` is what a thing is: one of the fifteen ontological clusters of the world-models corpus (`facets/clusters.yaml`, scheme `vercy-cluster`), the primary facet for internal meta-models and optional for external standards in v0.2. `industry` is which sector uses or governs it: the `vercy-industry` vocabulary (`facets/industry.yaml`), ISIC Rev.4 aligned, fifteen verticals and twelve horizontals, twenty-seven codes, multi-valued and swappable. State and Polity is one vertical among many (`government-public-sector`) and one cluster among fifteen (`polity`), never a privileged axis.
- The facet vocabularies under `facets/`: `clusters.yaml`, `industry.yaml`, `group-industry-map.csv` (maps each of the 37 external-registry Groups to one or more industry codes), and, describing how an external standard would compose, `compositional-roles.yaml` (the eight ARCH-016 roles R1 to R8) and `link-types.yaml` (the ARCH-016 mechanisms EMBED, REFERENCE, MIX-IN, COMPOSE, ALIGN, EXTEND, plus the literal N/A).
- The `industry` and `cluster` facets on the four internal seed entries: `vercy.aismm` (industry foundation-semantics and software-devops, cluster knowledge-information), `vercy.apmm` (industry foundation-semantics and education-skills, cluster organizations and people-groups), `vercy.plmm` and `vercy.elmm` (industry foundation-semantics, cluster organizations). The v0.1 free-text `industry: [software]` placeholder on `vercy.aismm` is replaced by the vercy-industry codes.
- The external catalogue tooling and the generated artifacts. `external/external-standards.csv` is generated by `tools/import_external.py` from the source catalogue `external/external-models.source.csv` plus `facets/group-industry-map.csv`, appending an `Origin` column (constant `external`) and an `Industry` column (the industry codes inherited from each row's Group). The build is deterministic: source columns keep their order, rows sort by Group then Acronym then Name, and the writer uses a fixed CSV dialect (LF terminator, minimal quoting), so a regenerated catalogue is byte-identical.
- `schema/external-standard.schema.json`: a JSON Schema (draft 2020-12) that validates one catalogue row projected as a JSON object. It is distinct from `registry-node.schema.json` and deliberately carries no MMDG node profile (no `csn`, `role`, `exports`, `requires`, `sync_contract`, or edges), which is the schema-level statement that a reference is not a node.

### Changed

- `schema/registry-node.schema.json` is extended toward v0.2, adding the optional `cluster[]` facet alongside the existing optional `industry[]`. The change is additive only: no field becomes required, so every pre-facet entry still validates, and backward compatibility with the v0.1 entries, the resolver, and the four v0.1 CI checks is preserved.

## [0.1.0] - 2026-08-10

### Added

- Initial public release of the Vercy meta-model registry, the running instance of the ELMM profile specified in ver-cy/elmm. The registry and the Meta-Model Dependency Graph (MMDG) are one artifact: every entry is at once a registry record and an MMDG node.
- The convergence contract: CI validates the whole entry against the ELMM node profile (carrying `csn`, `primary_namespace`, `role`, `fingerprint`, `source`, `steward`, `sync_contract`, `exports`, `requires`, `display_alias`, and optional `industry`, `origin`, `provenance`, `routing_hints`) and validates the entry's projected upstream field subset (`id`, `name`, `publisher`, `owner`, `version`, `kind`, `status`, `license`, `access`, `purpose`, `registered`, and `source` when access is public) against the unmodified upstream Meta-Universe registry-entry schema. Because the upstream schema is `additionalProperties: false`, the upstream check runs on the projection; the extension fields ride change requests upstream (`role` is CR-1; `sync_contract`, `exports`, `requires` are CR-2). `role` is the MMDG-normative class field; `kind` is mapped from it (`core` to `domain`, `landscape` and `kernel` to `enterprise`). The profile lifecycle value `active` corresponds to the upstream `stable` lifecycle in the projected subset.
- The four-record seed: `vercy.aismm` (core, external, v3.1.0), `vercy.apmm` (core, internal, v0.1.0, substance derived from a restricted-access source specification recorded as provenance), `vercy.plmm` (landscape, internal, v0.2.0), and `vercy.elmm` (kernel, internal, v0.1.0). The kernel carries empty `requires` and no outgoing edges; its knowledge of every node comes from the registry.
- The MMDG edge file `mmdg/edges.json` with two seed edges: `vercy.plmm` composes `vercy.aismm` (R2, declared_min 3.1.0, kinds software-product and entity) and `vercy.plmm` references `vercy.apmm` (R4, declared_min 0.1.0, kinds role and task). No `composes` or `references` edge leaves the kernel node.
- The four-type closed edge vocabulary: `composes`, `references`, `masters-link`, `deprecated-in-favor-of`, with `compositional_role` bound to ARCH-016 roles R1 to R8 and mandatory on composes and references edges. The seed exercises `composes` and `references`; `masters-link` and `deprecated-in-favor-of` remain in the vocabulary but are not drawn in this minimal graph.
- The deterministic resolver `resolver/resolve.py`: task descriptor in, context pack and Twin Composition Snapshot out, over the five-step algorithm (route by declared hints, transitive graph walk, Minimal Version Selection, pin at the declared ref, assemble). No wall-clock time and no randomness: timestamps come from CLI arguments or input fields, and `snapshot_id` is derived by hashing the resolved set with the edges digest and the task reference.
- Version resolution by Minimal Version Selection: `declared_min` is the sole resolver input, the resolution is the per-model maximum of declared minimums, and declared ranges are publish-time V-gate predicates only.
- The vendored JSON Schemas (draft 2020-12) from ver-cy/elmm: node profile, edge record, task descriptor, context pack, Twin Composition Snapshot.
- The four fail-closed CI checks, run in order by `ci/run.py`: schema validation of every record and edge; graph integrity (referential integrity of every edge endpoint, export coverage of every kind a `references` edge names, agreement between each `requires` minimum and the corresponding edge `declared_min`, acyclicity of `composes`, kernel isolation, and unique registry ids); resolver determinism and output validity; and zero-change registration. The example fixtures under `examples/expected/` are generated by running the resolver and compared by the resolver-determinism check.
- The worked example: `examples/task-product-impact.json` (a product-incident impact task across software and staffing) and `examples/walkthrough.md` narrating its resolution end to end.
- Repository meta: the BOOTSTRAP entry point per ARCH-017, CONTRIBUTING guidelines, and the Apache-2.0 license.
